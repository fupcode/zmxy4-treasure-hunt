# 状态编码 v4：96 维

`Env.state_encode()` 返回 `(96,)` 的 `float32` 数组。
环境、BC、PPO 和推理共用 `core/observation.py` 的字段定义；
`Env.state_schema_version=4`。状态码仍单独返回，不混入状态向量。

## 布局

索引采用 Python 左闭右开切片。

| 切片 | 维度 | 字段 |
| --- | ---: | --- |
| `0:2` | 2 | 玩家绝对归一化位置 `xn, yn` |
| `2` | 1 | 玩家剩余开火冷却 / 0.6，裁剪至 `[0,1]` |
| `3` | 1 | HP / 4，裁剪至 `[0,1]` |
| `4:7` | 3 | `pao, dan, fan` 拥有标志 |
| `7` | 1 | 关卡编号 / 4 |
| `8:17` | 9 | 地图类型 one-hot；起始区域全零 |
| `17:67` | 50 | 最近 5 个敌人，每个 10 维 |
| `67:88` | 21 | 最近 3 颗危险弹幕，每颗 7 维 |
| `88:96` | 8 | 8 个移动方向是否碰撞，`1=会撞，0=可走` |

每个敌人的字段：

```text
[present, dx, dy, box_left_dx, box_top_dy, box_right_dx, box_bottom_dy, fire_cooldown, in_fire_range, can_hit]
```

计算方式：

```python
dx = enemy.xn - player.xn
dy = enemy.yn - player.yn
box_left_dx   = enemy.x1 / MAZE_WIDTH  - player.xn
box_top_dy    = enemy.y1 / MAZE_HEIGHT - player.yn
box_right_dx  = enemy.x2 / MAZE_WIDTH  - player.xn
box_bottom_dy = enemy.y2 / MAZE_HEIGHT - player.yn
fire_cooldown = clip(enemy.fire_cool_down / 3.0, 0, 1)
```

中心使用当前实体归一化位置，框使用控制器实际采用的整数边界；
保留 `Enemy` 的下半框及普通敌人/BOSS 水平收缩规则。
`dx>0` 是玩家右侧，`dy>0` 是玩家下方。负值原样保留，不能裁剪到 `[0,1]`。
两个轴分别以整幅游戏窗口宽/高归一化，不是原始像素差。

敌人剩余子弹冷却以秒保存，每次有效场景更新都会递减，最低为 0。
沿用当前普通敌人 3 秒、BOSS 1 秒的估计；检测到归属该敌人的新子弹时重置冷却。
新敌人尚未观测到开火时按 0（可能随时开火）处理，短暂漏检仍更新冷却。
编码统一除以 3 秒，因此普通敌人刚开火为 1，BOSS 刚开火约为 0.333。
专家安全判定也依据剩余冷却大于 0，不再使用 `fired` 布尔字段。

每颗弹幕的字段：

```text
[present, right, down, left, up, dx, dy]
```

其中 `dx=bullet.xn-player.xn`，`dy=bullet.yn-player.yn`，
方向 one-hot 表示弹幕本身的飞行方向，不是它相对玩家的位置方向。

敌人与弹幕继续按逻辑地图上的玩家曼哈顿距离选择最近对象，不足时整槽补零。
存在标志用于区分空槽与“确实位于玩家位置”的对象。
只有输入槽位限制为 5 敌人、3 子弹；内部追踪列表及专家策略仍可使用全部对象。

碰撞标志与动作编号 `1..8` 严格同序：

```text
[右, 下, 左, 上, 右下, 左下, 右上, 左上]
```

通过 `Map.is_move_collision()` 计算，横向、纵向均检查 3 个逻辑像素；
斜向叠加为横向 3、纵向 3，逐格检查整段路径，不额外检查两侧格子；角色碰撞范围由扩张后的地图表示。碰撞检测包括地图边界、静态障碍与战斗禁区，
不把敌人/弹幕当作墙，不阻止动作执行，也不额外计算专家危险图。

## 数值示例

玩家位于 `(0.5, 0.5)`，敌人位于 `(0.6, 0.4)`，
实际整数碰撞框为 `(176, 76, 208, 88)`，对应归一化 `(0.55, 0.38, 0.65, 0.44)`：

```text
敌人槽：[1, 0.1, -0.1, 0.05, -0.12, 0.15, -0.06, 0]
```

一颗位于 `(0.4, 0.5)`、向右飞的弹幕：

```text
弹幕槽：[1, 1, 0, 0, 0, -0.1, 0]
```

其余不存在的敌人、弹幕槽全部补零。

## 专家数据和 checkpoint 兼容

新版专家运行目录的 `config.json` 必须包含：

```json
{
  "schema_version": 4,
  "observation_schema_version": 4,
  "observation_dim": 96,
  "actions": ["stop", "Right", "Down", "Left", "Up", "DownRight", "DownLeft", "UpRight", "UpLeft"]
}
```

NPZ 的 `obs` 为 `(N,96)`；清单、动作和其他采集字段保持原有含义。
BC/PPO checkpoint 保存 `observation_schema_version=4` 和输入维度。
加载器同时校验版本和维度，避免相同维度但不同字段语义的存档被误读。

v4 每个敌人新增两个标志：

- `in_fire_range`：按 `Map.fire_distance()` 的方向优先级与敌人碰撞框对齐，且到敌人中心的轴向距离在射程内。
- `can_hit`：已对齐且在射程内，并且从玩家格到敌人中心投影格的射线上没有障碍物，检查包含两端。

未对齐或空槽位时两项均为 0。地图使用专家开火判定所用的膨胀地图。
`can_hit=1` 表示当前可射中；`in_fire_range=1, can_hit=0` 表示射程内但有遮挡。
v2 的 86 维专家数据可使用地图编号、关卡、角色绝对坐标和敌人相对坐标/整数边界框重建这两个标志；
已用仓库外脚本迁移并合并 `data/expert`，清单保留原始来源，旧目录在仓库外备份。
旧数据坐标为 float32，重建无法恢复被量化前的亚像素精度。
v3 与 v4 均为 96 维，但末项语义不同，因此升级版本号；旧 checkpoint 需要重新训练，不能直接续训。
默认新模型为 `96 → 256 → 256 → 256 → 9/1`。

## 后续建议

先保持 `256×3` 隐藏层，比较学习曲线与实际通关表现，再决定网络容量。
后续可补充本关剩余战斗时间。
只有 3 个弹幕槽时，关注第 4 颗及更远弹幕造成的受伤；
若确实遗漏关键威胁，再比较“按距离选取”与“按对准程度/接近方向选取”。
当前已包含边界框、碰撞标志与敌人冷却；速度和本关剩余时间尚未加入。
